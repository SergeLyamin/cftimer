# Design

## Context

См. [proposal](proposal.md). Основан на проверенном локальном кандидате 0.1.5; по разрешению владельца 27.10.2026 реализация QR начинается в изолированной рабочей копии параллельно выпуску локального UI. Аппаратная приёмка остаётся открытой до пилота. Требуется несколько независимых залов; архивный глобальный host запрещён архитектурой. Пилот с облачным интернетом, но локальный отсчёт переживает потерю relay.

## Goals / Non-Goals

**Goals:** отдельные room/host/controller полномочия, deterministic command handling, заметная недоступность remote, восстановление из snapshot без остановки дисплея.

**Non-Goals:** distributed consensus, несколько writer, shared auth/accounts, база тренировок, LAN transport, соревнования с синхронизацией нескольких экранов.

## Decisions

1. **Один Node процесс + ws.** Комнаты in-memory; API создания/приглашения и WebSocket messages валидируются общей строгой схемой. Redis/горизонтальное масштабирование не требуется для пилота; добавление реплик без общей модели состояния запрещено. Конкретный HTTP framework вторичен.
2. **Display authoritative.** Server owns authorization/room epoch; display owns timer state/revision. Только display исполняет actions и выдаёт ACK результата. Control revision увеличивается при принятой команде/автоматическом переходе фазы, не при каждом UI tick. Снимки также имеют возрастающий snapshot sequence для порядка внутри одной revision и epoch.
3. **Технические credentials без аккаунтов.** Room ID не даёт права host. Случайный host secret (≥128 бит) живёт в памяти документа компьютера. QR связывает с одной display session; приглашение обновляется после использования/120 с. Secret во fragment очищается из URL сразу после чтения. Первый претендент при свободном пульте получает credential автоматически, без локального approval/PIN. Общий acquisition path для первого подключения, accept, takeover после 60 с и explicit release: сервер резервирует одного кандидата, повышает controlEpoch, экран подтверждает fencing, лишь затем новый пульт получает статус ready. При недоступном экране кандидат остаётся waiting/no display, не становится готовым управляющим. QR разрешает запрос доступа, не постоянное управление.
4. **Передача между пультами.** У владельца один pending requestId на 20 с. Accept/refuse поступают только от действующего controller. При accept сервер сериализует передачу, увеличивает controlEpoch, сообщает экрану; выдача новому пульту подтверждается после того, как экран принял новую controlEpoch и fenced старую. Delayed команды старого поколения отклоняет также экран. Запоздалое accept, duplicate и конкурирующие запросы не могут создать двух writer. Refuse/timeout при живом владельце не выдаёт доступ. 20 с ограничивают только approval request, не отдельное ожидание освобождения: если владелец пропал, связанный претендент может оставаться на экране ожидания до lastContact+60. При возврате владельца прежний истёкший requestId не оживает: нужен новый запрос. «Отменить запрос» отменяет также ожидание acquisition. Истечение QR после валидного связывания не обрывает ожидание; токен ожидания не даёт права командовать. Предложение anti-spam: один pending request и не более одного нового запроса от претендента за 30 с.
5. **60 секунд без связи.** Server-side lastContact обновляется подтверждённым heartbeat текущего пульта; grace считается от него, а не от обнаружения разрыва. После 60 с новый претендент может получить пульт через тот же acquisition path с display ACK, без согласия прежнего владельца. Если старый вернулся раньше выдачи новому, может восстановить credential; гонку решает один server event loop. Если другой уже получил право, старый видит replaced и не переигрывает offline actions. Explicit «Отключить пульт» сразу начинает отзыв, повышает controlEpoch и fences владельца none на экране; доступ нового владельца ожидает подтверждения экрана. Блокировка телефона сама по себе не означает уход, если связь остаётся живой.
6. **Команды и ordering.** Публичные намерения: start(config), pause, resume, restart, edit, returnToMenu, repeat. Отдельного configure/finish нет: черновики форм локальны, start проверяет и применяет целую конфигурацию атомарно. Restart только paused повторяет с подготовкой; edit только paused прекращает прежний отсчёт и открывает параметры; returnToMenu подтверждается UI при активной программе; repeat только completed. Local/remote используют один DisplayRuntime и одну таблицу предусловий. Runtime один раз читает монотонное now, продвигает время, проверяет expectedRevision, выполняет намерение, сохраняет результат и публикует snapshot; внутри нет await/нового независимого замера времени. Прикладная revision отдельна от snapshot sequence и внутренних счётчиков ядра. Нет silent no-op с успешным ACK.
7. **Результаты и поздняя доставка.** Envelope содержит protocolVersion (handshake), roomId, sessionEpoch, controlEpoch, commandId (=sessionEpoch_controlEpoch_commandSeq), commandSeq, expectedRevision, sampleSeq и intent. Авторизация/актуальное поколение проверяются до dedup, dedup — до revision. Один незавершённый mutating command на пульт. Монотонный watermark плюс последний терминальный результат ограничивают память; старый seq никогда не исполняется заново, удалённый результат — history_expired, не ложный успех. Тот же ID с другим содержимым отклоняется. Pending-конверт и счётчик сохраняются до отправки; reconnect/reload сначала запрашивает snapshot и результат, не повторяет команду автоматически. После 3 с без ACK — unknown. Новый запуск команды допустим только в течение 3 с от метки snapshot, выданной экраном; экран проверяет sampleSeq/срок по своим часам. Повтор исполненного ID возвращает результат и после истечения. Невыполненная просроченная команда может быть окончательно отклонена при явной попытке; unknown не означает отмену.
8. **Clock projection.** Snapshot несёт phase, elapsed/remaining, status, revision, sequence, timing sample. Phone оценивает отображаемое время по clock-offset/RTT handshake и монотонным часам локально; сырые performance.now разных устройств не сравниваются. Мобильное время приблизительно; authoritative display только на PC. Начальный acceptance target p95 расхождения ≤250 мс при RTT≤100 мс, два устройства в foreground; отдельно от цели локального timer-core.
9. **Disconnect/cleanup.** Heartbeat detects missing peer ≤10 с; экспоненциальный backoff с jitter и максимумом 10 с. Host disconnected 10 мин → cleanup room. Сессия max 8 ч; relay restart → new epoch, новый pairing, местный таймер не сбрасывается. При room expiry host UI объясняет необходимость нового соединения, сохраняя программу.
10. **Abuse controls.** WSS/HTTPS, same-origin allowlist, 16 KiB frame limit, pairing 5/min per source плюс глобальный budget и лимит запросов на экран. Команды ≤10/sec/controller с небольшим burst; превышение отклоняется. Не логировать secrets/QR; Referrer-Policy no-referrer на pairing/controller; auth/session API не кэшировать service worker. Origin не заменяет token authorization.
11. **Один transport host.** Каждое успешное возобновление привязано к server-side connection generation, прежний transport fenced и не публикует state/ACK. Host credentials живут в памяти текущего документа; новая вкладка/reload создаёт новую комнату и не наследует host через localStorage/sessionStorage. Компьютерный reload создаёт новый idle runtime/room без восстановления active snapshot. Credential пульта допустим в sessionStorage вкладки телефона для reload; recovery не выдаёт новые права и всегда проверяет current controlEpoch. У нового документа телефона без действующего credential — обычный запрос доступа. Копия вкладки не создаёт второго writer: у credential одно актуальное поколение socket. При закрытии экрана old room закрывается best effort и перестаёт отвечать; при reload новый документ создаёт новую sessionEpoch. Таймер старого закрытого документа не переносится.

12. **Журналы вместо кабинета.** JSON stdout с server timestamp, eventId, несекретным correlation ID, mode/source/outcome/reason/latency. Клиентские события валидировать/rate limit; серверные решения логировать на сервере. Bounded local queue 200 событий/24 ч для offline usage — предложение; дедуп eventId в report. Retention предложение 14 дней/1 GiB. tools/report-usage.mjs и tools/trace-session.mjs читают export/stdin по SSH, публичных admin endpoints нет. Источники и поля — [operations](../../../docs/operations.md). Метрика/Google — отдельные необязательные adapters после определения оператором юрисдикции/потоков данных, выполнения применимых требований и предоставления ID; BL-02 описывает подготовку политики.
13. **Haptics.** Опционально после user gesture, visible page и подтверждённой команды; feature detection плюс тест пользователем. Не обещать iPhone/Safari или background alarm; отсутствие физического отклика не ошибка таймера.

14. **Вход и QR visibility.** Только явный pairing route открывает пульт; обычный адрес смартфона открывает личный таймер из bootstrap. Resize не меняет роль. По решению владельца 27.10 на большом экране кнопка QR находится в шапке слева от настроек, включая setup/timer; панель закрыта по умолчанию, раскрывается по нажатию и возвращает фокус после закрытия. Зелёный огонёк кнопки означает наличие подключённого действующего пульта при доступном relay. Шапка телефона содержит «Пульт» и точку с текстовым статусом; room/screen номера в UI не выводятся. Мягкий radial-фон пульта сохраняется по одобренному направлению референса 2026-10-22-remote-flow-v1.png. Сворачивание не отзывает credential и не отменяет связанное ожидание; при раскрытии показывается действующее приглашение или no connection. Ручной ввод кода/ссылки и casting вне этого change (BL-06/07); прежние PNG с кодом — reference, не обязательство реализации.

15. **Границы модулей.** timer — детерминированные фазы/время; application — документный DisplayRuntime, транзакции и согласованное состояние; protocol — versioned DTO/runtime validation; remote — transport/display bridge/controller client; server — комнаты и тонкий HTTP/WS adapter; ui/platform — представление и браузерные эффекты. Обычные модули одного проекта, без event bus/DI framework/пакетного monorepo. Активный UI берёт конфигурацию только из snapshot, черновики остаются на устройстве до start. Wire DTO отдельно от внутреннего класса ядра.
16. **Жизненный цикл и подписки.** Runtime создаётся в bootstrap документа, не в React render. getSnapshot — чистое чтение cached immutable объекта, tick и execute публикуют изменения. StrictMode/remount не создаёт вторую комнату. Маршрут /remote определяется до создания TimerEngine/audio/host; ошибочное приглашение остаётся remote error. Доступность QR фиксируется при входе: короткая сторона viewport >640 CSS px (текущая граница компактной композиции), resize меняет только layout. Серверная метка экрана остаётся техническим полем протокола, но не выводится в UI. Пульт не играет звуки и не может снять browser activation restriction на PC.
17. **Fencing и recovery выдачи.** Room state machine различает free/assigning/owned/revoking, pending approval отдельно. Каждая выдача/отзыв имеет acquisitionId; ACK принимается только для актуального ID/epoch/controllerGeneration и текущего host socket. После начатого fencing поколение не откатывается. Release и cancel после начала выдачи fences none новым поколением. Повтор той же установки идемпотентен. Controller resume меняет transport generation, заново подтверждается экраном, сохраняет dedup текущей controlEpoch. Клиенты игнорируют callbacks старых socket. Повтор join с тем же invitation+claimSecret восстанавливает тот же credential; другое использование одноразового приглашения отклонено. Claim secret создаётся телефоном до отправки, credential выдаётся сервером.
18. **Ресурсы и защита.** Секреты — 32 случайных байта. Auth первого сообщения за 5 с; Origin проверяется до upgrade, tokens только в сообщениях WSS. Compression выключена; max message 16 KiB. Ограничиваются комнаты, sockets, waiting principals, создание комнат и размер outbound buffer; лимиты конфигурируемые, исходные 32 комнаты/128 sockets/4 ожидающих на комнату. При переполнении соединение закрывается и восстанавливается из snapshot, очередь не растёт. Не доверять X-Forwarded-For без явного доверенного proxy. CSP/Referrer-Policy/no-store на динамических API, без сторонних скриптов пульта; в логах только allowlisted поля.
19. **Версии и PWA.** protocolVersion=1 согласуется до доступа, appVersion только диагностическая. Несовместимость блокирует пульт с объяснением, не reload работающего экрана. App shell /remote кэшируется отдельно от auth/session/ws; fallback только известным navigation paths, API не превращается в index.html. Прежняя политика отложенной активации SW сохраняется. Snapshot отправляется при semantic change и максимум раз в секунду для clock sample; RAF не рассылается по сети.
20. **Поэтапная приёмка.** Чистые protocol/runtime/room tests проверяют фундамент. Для изменённого интерфейса сначала только нужные desktop checks и показ владельцу; после нового UI approval — mobile, cross-browser, регрессии, PWA и полный сквозной прогон. Приёмка UI/выпуск 0.1.5 в другом чате не считается одобрением нового QR UI или разрешением его публикации.

## Risks / Trade-offs

- Публичный QR позволяет любому получить свободный пульт → это подтверждённая модель продукта; активный владелец защищён запросом передачи и rate limit.
- Блокировка телефона может привести к 60 секундам без heartbeat → уведомить о возможности передачи; не обещать распознавание физического ухода.
- In-memory state исчезает при рестарте → осознанно повторный pairing; тренировка не прерывается. Персистентные комнаты позже.
- Сеть может задержать или повторить команду → epoch/revision/dedup и ACK от экрана; пользователь видит unknown, не ложный успех.
- Два конфликтующих действия требуют повторного намерения → это предпочтительнее неожиданного reset/паузы; показать актуальное состояние.
- Cloud relay не работает без WAN → локальный экран работает; LAN mode отдельный продуктовый объём.

## Migration Plan

После разрешения владельца на изолированную разработку реализовать application contract и protocol, rooms, display integration, controller UI; для нового UI соблюсти desktop review gate. Тестировать два зала и реальные WSS через staging proxy. Deployment change выбирает host/domain/rollback. При откате remote экран не должен терять локальный mode; архивный общий server.js не используется. До полного прохождения сценариев этот change остаётся открытым.

21. **Компактный пульт после просмотра владельца.** Header15px, статус — menu trigger, disconnect с красной точкой внутри меню. Mode caps+back слева под header; активный back требует подтверждения. Нейтральная pause/resume56px, sidehit48px. Удалены ready helper, нижние menu/disconnect и footer пояснение звука. ACK/revision/право доступа не меняются. Общая палитра preparation #F5F5F5 согласована с bootstrap.

22. **Нижнее управление и спокойный ACK feedback.** По последнему desktop review preparation белая #F5F5F5, обычные зазоры timeline6px вместо3px. Controls пульта располагаются в нижней thumb-зоне примерно10svh от нижнего края, с резервом контента и safe-area. Обычный pending ACK обозначается блокировкой повторного действия без вспыхивающей предупреждающей плашки. Unknown спустя установленный срок и реальные ошибки не скрываются.

23. **Шапка и фон пульта, уточнение 27.10.2026.** Зелёный индикатор на QR-кнопке дисплея означает одного готового controller: credential/controlEpoch актуальны, связь подтверждена и display принял выдачу права. При известном disconnect индикатор гаснет, даже если lease ещё в 60-секундном grace. Размер/место кнопки не меняются; tooltip/доступное имя и текст панели объясняют состояние. На телефоне шапка «Пульт» + словесный статус: подключён/подключение/ожидание/нет связи/отключён, без пользовательских номеров и технических IDs. Зелёный только после ACK выдачи права и свежего snapshot. Графитовый CSS radial-gradient с широким статичным мягким свечением в верхней части повторяет настроение design/concepts/2026-10-22-remote-flow-v1.png; яркость/точные оттенки — предмет staged desktop review перед мобильной приёмкой. Без новых assets/сети и без изменения фона локального рабочего дисплея. Конкретные контраст/размеры статуса проверяются в браузере.
