# Путь к запуску на сервере

Статус 23.10.2026: на https://timer.lyamin.org/ опубликован статический релиз `082c009` с новым интерфейсом; сборка из `dist/`. QR relay ещё не реализован. Результаты предыдущего развёртывания сохранены ниже как история.

## Куда размещать

Из архивной документации известен только адрес **https://timer.lyamin.org**. Старый ecosystem.config.js указывает процесс PM2 `timer`, server.js и порт 3001. Скрипт deploy.sh предполагает запуск уже на сервере: git pull, npm install, сборка старого CSS и pm2 restart. Он не содержит адреса SSH, провайдера, каталога сайта или конфигурации HTTPS. Это исторические сведения, не подтверждённое состояние сервера. Старый скрипт для новой версии не подходит.

## Проверка dev7 по SSH

Проверено 22.10.2026 по указанию владельца. Алиас `dev7` подключается как `develop7`, hostname `vm-b911eb17`, Linux. На сервере работает Nginx. Домен включён ссылкой `/etc/nginx/sites-enabled/timer.lyamin.org.conf` на `/etc/nginx/sites-available/timer.lyamin.org.conf`.

Файл конфигурации имеет права root:root 0600. `develop7` не может его прочитать, а `sudo -n` требует пароль. Есть отдельный пользователь `timer` и закрытый для develop7 каталог `/home/timer` (0750). Вход `ssh -l timer dev7` текущим ключом отклонён. В PM2 пользователя develop7 таймера нет; процессы других пользователей этим списком не проверены. Запрос HTTPS с dev7 возвращает HTTP 403 (Nginx); причина без конфигурации не установлена. Каталог раздачи, upstream, сертификат и текущая версия приложения ещё не установлены.

Для следующего шага нужен разрешённый SSH-доступ пользователя timer либо административное чтение конфигурации и доступ к целевому каталогу. После чтения конфигурации можно подготовить точную процедуру релиза/отката. Проверка не изменяла сайт, конфигурацию или процессы таймера. Секреты в репозиторий не записываются.

## Деплой текущей локальной версии

Сейчас достаточно статического HTTPS-хостинга: Node нужен для сборки, постоянно работающий backend не требуется. Предпочтительный путь при наличии старого VPS — разместить новую сборку на тестовом поддомене того же сервера, проверить, затем отдельно переключить основной адрес.

1. Сборка из зафиксированного коммита: `npm ci`, `npm run lint`, `npm test`, `npm run build`; браузерные проверки — `npm run test:e2e`.
2. Передать **всё содержимое dist/** в отдельный каталог релиза. Архив, node_modules, исходники и tooling на публичный сайт не выкладывать.
3. Настроить HTTPS и статическую раздачу через существующий Caddy/Nginx. `/sw.js`, `/index.html` и `/manifest.webmanifest` должны проходить revalidation (`Cache-Control: no-cache`); файлы `/assets/` с hash в имени можно кэшировать на год как immutable. Не возвращать index.html вместо отсутствующего JS/CSS: для этих путей нужен 404.
4. Выполнить smoke test с реального домена: режимы, звук, HTTPS, SW, cached offline reopening. Аналитику пока не подключать; проект политики ещё не заполнен.
5. Сохранить предыдущий каталог релиза и конфигурацию. Переключать корень сайта атомарно; старые hash-assets сохранять доступными для открытых вкладок. Для отката переключить каталог обратно, затем проверить поведение service worker на уже посещавшем сайт браузере.

Публичный просмотр для тестирования не означает допуск в зал: аппаратная приёмка остаётся открытой. Подготовленные локальные команды и доказательства — [отчёт](implementation-2026-10-22.md).

## Следующий этап: схема с QR-пультом

Один VPS/контейнерный хост с Node LTS relay, статическими assets и HTTPS reverse proxy (Caddy либо Nginx). Один процесс комнат достаточен для 1–3 залов. БД/Redis/кластер не добавлять до потребности. Провайдер и цена выбираются после ответа владельца.

Телевизор подключён к компьютеру по HDMI, браузер открыт на экранном URL. Телефон ходит к тому же HTTPS-сервису по Wi-Fi или мобильному интернету; общая LAN при облачном relay не обязательна. При исчезновении WAN локальный экран продолжает, remote недоступен до восстановления связи.

## До staging

- Для релиза с пультом завершить bootstrap и remote changes; чистая установка и production build воспроизводимы.
- Зафиксировать Node/runtime dependencies, CI команды, переменные окружения в `.env.example` без секретов.
- Реализовать health/readiness, WSS upgrade, Origin allowlist, payload limits, rate limit, cleanup комнат.
- Проверить два зала, истечение/отзыв доступа, reconnect, рестарт relay и продолжение экранного таймера.
- Логировать технические причины ошибок и версии без токенов/приватных QR ссылок.
- Проверить лицензионный текст, происхождение/права на используемые шрифты и звуки; не переносить непроверенные assets автоматически.

## Перед пилотом

- Выбрать поддомен staging, открыть HTTPS; не заменять неизвестный live-сервис без резервной копии и понимания его текущей версии.
- Провести E2E через реальный reverse proxy с WSS и service worker.
- Подготовить воспроизводимый релизный артефакт, commit/version и предыдущий релиз для отката; проверить откат на staging.
- Обновление service worker активировать между занятиями. Рестарт relay лишает связи, но не останавливает локальный отсчёт.
- Проверить компьютер/браузер/телефон зала, звук, полноэкранный режим, запрет сна, масштабирование экрана.
- Иметь запасной обычный таймер на первых испытаниях и короткую инструкцию для пользователя.

## Что нужно знать о сервере

Провайдер, ОС/контейнерный способ запуска, домен, где расположен старый сайт, допустимые расходы и кто управляет DNS. Секреты передавать через установленный безопасный способ доступа, не записывать в docs/specs.

Когда эти сведения появятся, создать отдельный OpenSpec change с конкретными конфигурациями, командами запуска, мониторингом и процедурой отката. Текущий документ — критерии готовности, не якобы работающая инструкция деплоя.

Серверное хранение ограничено временными сессиями и журналами. Deployment должен настроить ротацию/лимит логов и доступ к CLI по SSH; публичная админка/аккаунты не нужны. Требования — [operations.md](operations.md).
