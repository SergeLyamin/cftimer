# ADR-001: OpenSpec для перезапуска CF Timer

Дата: 22.10.2026. Статус: принято и внедрено для процесса разработки. Выбор SDD не утверждает все продуктовые гипотезы.

## Решение

OpenSpec **1.14.3**, встроенная схема `spec-driven`, core-интеграция Codex. Установка локальная и изолированная в `tooling/openspec`, без глобального CLI. Официальный `init` создал `.agents/skills/openspec-*`; версия закреплена lock-файлом.

## Почему

Проект уже прошёл неудачное переписывание и накопил несколько противоречивых описаний. Нужны небольшие изменения: требования → техническое решение → задачи → код → проверка → включение в действующую спецификацию. OpenSpec делает явным различие между baseline и delta changes. Для одного владельца и AI-агентов это помогает контролировать объём и не выдавать старые планы за реализацию.

| Критерий | OpenSpec | GitHub Spec Kit |
| --- | --- | --- |
| Существующий проект | Явные текущие specs и изменения по возможностям | Также применим; не ограничен greenfield |
| Рабочий процесс | Proposal/design/delta specs/tasks; обновление baseline при завершении | Constitution/specify/plan/tasks/implement и проверки согласованности |
| Организационная польза | Небольшой инкремент, удобная история контрактов | Подробная дисциплина проекта, шаблоны и расширяемые workflows |
| Дополнительные инструменты | Node, который нужен приложению | Python 3.11+ и uv для Specify CLI |
| Риск для CF Timer | Принять заполненные документы за готовую функцию | Обслуживать слишком большой процесс до проверки пользы продукта |

Выбор — оценка соответствия нашему объёму, не утверждение о превосходстве OpenSpec во всех проектах. Если появятся несколько команд, требования аудита или сложная программа поставки, решение можно пересмотреть.

## Как применено

- В `openspec/specs/project-workflow/` — уже действующий процесс и правила хранения фактов.
- Продуктовых baseline specs пока нет: приложение архивировано.
- Два changes: локальный таймер, затем QR remote. У обоих задачи остаются `[ ]` до реализации и проверок.
- `docs/` объясняет решения; не дублирует все acceptance criteria.
- Архивные `.kiro`, старые документы и code snapshots не являются источником новых обязательств.
- `npm run spec:validate` проверяет все specs/changes в strict-режиме. Это не build, E2E или доказательство надёжности.
- `archive`/`sync-specs` выполняются после проверки реализованного поведения. Не переносить перспективные требования в baseline только потому, что CLI позволяет это сделать.
