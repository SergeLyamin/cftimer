## Вывод

На момент начала аудита рабочее дерево представляло собой **незавершенную заготовку переписывания**, а не готовый к публикации таймер. Есть типы, каркас приложения, EventBus, CSS и HTML с надписью «Загрузка...». Самого движка таймера, экранов, сервера, QR pairing и рабочего удаленного управления в этой заготовке нет.

После аудита по указанию владельца наследие перенесено в [archive/legacy-worktree](../archive/legacy-worktree/). Все пути `src/...`, `public/...`, `control.js`, `package.json` и configs ниже обозначают **расположение до архивирования**; после переноса искать их с префиксом `archive/legacy-worktree/`. Номера строк относятся к проверенному снимку. Корень проекта после архивирования содержит документацию и спецификации; новая реализация — отдельное будущее изменение. Ошибки старого scaffold не следует выдавать за ошибки еще не написанного нового приложения.

Возобновлять проект разумно небольшими законченными этапами: сначала воспроизводимая сборка и локальный таймер, затем экран зала и безопасный пульт. Полный перенос старой архитектуры не нужен. Старую реализацию из Git стоит использовать как источник поведения и визуальных решений, проверяя каждый сценарий заново.

## Блокирующие проблемы

### P0 — Невоспроизводимая сборка

1. `package.json` описывает `crossfit-timer-v2` версии `2.0.0`, TypeScript/Vite/Jest. Корень `package-lock.json` все еще описывает `cftimer` версии `1.0.0` с Express/QRCode/Playwright и другим набором зависимостей. Чистую установку нельзя считать проверенной; сначала нужно согласовать manifest и lock.
2. `tsconfig.json:22` ссылается на отсутствующий `tsconfig.node.json`.
3. `src/app/App.ts:3` и `src/app/App.ts:4` импортируют отсутствующие StateManager и TimerEngine. `src/services/EventBus.ts:1` импортирует отсутствующий `services.types`.
4. HTML находится только в `public/index.html`. `vite.config.ts:4` не задает иной root или HTML input; корневого `index.html` нет. Это отдельный структурный блокер стандартной Vite-сборки, выявленный чтением конфигурации; запуском Vite он не подтвержден.
5. `public/index.html:7` ссылается на `/dist/styles.css`, которого нет. Конфигураций PostCSS/Tailwind в текущем дереве нет, хотя CSS использует их директивы. Само наличие зависимости не подключает обработку CSS.

### P0 — Нет исполняемого продукта и сервера

У текущего дерева нет timer engine, UI экранов, WebSocket server, session lifecycle и QR pairing. В package scripts отсутствует `start`. Старые инструкции `npm start`, `npm run css`, `npm run deploy`, пути `www/`, `server.js`, `ecosystem.config.js` и `deploy.sh` не соответствуют текущему checkout.

### P1 — Остаточный remote client нельзя переносить без переработки

`control.js` находится вне TypeScript include и не проверяется текущим `type-check`:

- `control.js:18`, `control.js:61`, `control.js:65`: вызываются отсутствующие `showError`, `updateState`, `updateSettings`.
- `control.js:38`: JSON парсится без обработки ошибок и проверки схемы сообщения.
- `control.js:73` и `control.js:96`: `screenName` из входящего сообщения попадает в HTML-атрибут через `innerHTML`; при подключении такого клиента к недоверенному источнику возникает HTML injection/XSS риск. В текущем приложении этот код не подключен, поэтому это риск повторного использования, а не доказанная работающая production-уязвимость.
- `control.js:31` и `control.js:118`: передаются `timerId` и команда, но клиент не показывает протокола авторизации, срока жизни доступа или разграничения controller/display. Сервер отсутствует, поэтому его проверки неизвестны.
- `control.js:45`: фиксированный reconnect без backoff/jitter, cleanup или восстановления подтвержденной версии состояния.

QR должен давать краткоживущее приглашение к конкретному экрану. Публичный ID комнаты и право управлять ею — разные сущности. Для зала нужны отзыв доступа, явный активный пульт, изоляция комнат и понятное восстановление после потери сети.

### P1 — Нет проверки продуктовых сценариев

`npm test` вызывает Jest, а имеющиеся тесты написаны под Playwright. `@playwright/test` не объявлен в текущем package manifest. Jest/ESLint configs не найдены. В `playwright.config.ts` выключены local baseURL и webServer, а тесты открывают `playwright.dev`.

Такие тесты не подтверждают ни точность таймера, ни QR, ни remote. Нужны тесты временных переходов и двух изолированных комнат, а также браузерный сценарий «экран + телефон».

Критические особенности **исторического**, не текущего кода:

- `d3e506f:server.js` хранит один глобальный `host` и общий Set controllers. Все команды идут этому host, обновления — всем controllers. Нет разделения залов/комнат.
- В том же сервере любое соединение может через `init` объявить себя host; проверки роли отправителя команды не реализованы. QR ведет на общий `/control`, без отдельного invitation/session token.
- `d3e506f:www/js/main.js` создает четыре специализированных таймера и один базовый Timer. Базовый constructor создает WebSocket и keyboard handlers; это приводит к нескольким соединениям и обработчикам на одной странице. Сервер при этом хранит только последний host.
- `d3e506f:www/js/services/WebSocket.js:27` при каждом `init()` создает новый interval переподключения. `cleanup()` его не очищает.
- Исторический monolith `www/timer.js` считает секунды через `setInterval` и decrement. Его не нужно механически копировать: задержка callback может накапливать ошибку. В указанном коммите index подключает модульный `js/main.js`, поэтому monolith нельзя выдавать за единственный активный runtime.
- Tailwind уже использовался и там (`^3.4.17` в историческом package manifest).

Историю следует читать или извлекать в изолированный каталог. Восстановление старых файлов поверх незакоммиченного дерева рискует потерять пользовательскую работу.

## Варианты стека и рекомендуемое направление

| Вариант | Когда подходит | Компромисс |
|---|---|---|
| TypeScript + Vite + небольшой vanilla UI | Один экран и очень ограниченные настройки | Меньше зависимостей, но ручное управление DOM и двумя интерфейсами быстро усложняется |
| **TypeScript + Vite + React + Tailwind** | Экран зала, отдельный пульт, пресеты и разные состояния подключения | Дополнительный UI framework; удобнее поддерживать состояния и общий набор компонентов |
| Полноценный SSR/full-stack framework | Публичный SEO-контент, развитый кабинет и серверные страницы становятся ядром продукта | Сейчас добавляет инфраструктуру, не решая главные задачи точности и remote |

Предпочтение — второй вариант, если продукт действительно развивается в сервис для залов. Это архитектурная рекомендация, а не утверждение, что текущий UI уже React. Точные поддерживаемые версии инструментов, Node и browser baseline необходимо закрепить при bootstrap после сверки с официальной документацией; старые major из package.json не являются целевым решением.

Предлагаемое разделение:

1. `timer-core`: чистая модель фаз и команд, независимая от DOM и сети; elapsed/deadline вместо подсчета callback-вызовов; возможность подставить часы в тестах.
2. `display`: крупное время, текущая фаза, звук и локальное управление. Активная тренировка продолжает идти при потере remote-соединения.
3. `controller`: настройки и команды; отображает подтвержденное состояние экрана, а не только локально нажатую кнопку.
4. `session-service`: изолированные комнаты, pairing, роли, срок жизни доступа, версии состояния, command IDs/acknowledgements и reconnect snapshot.
5. Node WebSocket relay как небольшой отдельный сервис; хранилище добавлять по требованиям пресетов, аккаунтов и восстановления. Redis/microservices не обязательны для пилота с одним instance.

Для согласованного пилота экран на PC — владелец выполняемой тренировки и локального времени; сервер отвечает за комнаты, авторизацию и пересылку команд. Экран подтверждает команды и публикует состояние. Это позволяет продолжать уже запущенную тренировку без сети; пульт в этот момент показывает отсутствие связи и не обещает выполнение команд. Работа пульта без интернета и загрузка страницы заново из PWA cache не входят автоматически в этот сценарий. Если понадобятся несколько синхронных дисплеев, ownership и правила failover нужно спроектировать отдельно; два независимых автора состояния недопустимы.

Tailwind помогает реализации стилей, но не определяет дизайн. Сначала нужны токены размеров, контраста, фаз и расстояний, а также отдельные состояния display/controller. Нельзя оценивать визуальное совпадение с референсами по наличию CSS framework.

## Порядок восстановления и готовность к серверу

**Этап 1 — Собираемый baseline:** согласованный package/lock, корневой HTML, рабочие TypeScript/Vite/CSS configs, единый test runner и CI. Проверка чистой установки и production build.

**Этап 2 — Локальная тренировка:** AMRAP/FOR TIME/interval с детерминированными переходами, pause/reset, sound unlock, fullscreen и recovery. Тестировать паузу, долгую задержку callback и переход через несколько фаз.

**Этап 3 — Один зал, экран + пульт:** QR и короткий код как fallback, привязка конкретного телефона к экрану, подтверждение команд, reconnect без двойного старта, отзыв контроллера, продолжение таймера при обрыве сети.

**Этап 4 — Пилот на сервере:** HTTPS/WSS и reverse proxy, room isolation и authorization tests, limits/validation сообщений, health/readiness, перезапуск процесса, логи без токенов приглашения, rollback. Проверить хотя бы два независимых зала одновременно.

**Этап 5 — Реальные устройства:** большой монитор, iOS/Android, слабый Wi-Fi, потеря/восстановление сети, блокировка телефона, звук и полноэкранный режим. Браузерные ограничения fullscreen/audio нужно учитывать в onboarding и не обещать произвольную удаленную активацию без проверки на целевых устройствах.

До этих этапов разворачивать текущее дерево как общедоступный сервис для залов нельзя считать завершенным или проверенным результатом. Главный риск проекта сейчас — отсутствие согласованной рабочей реализации, а не отсутствие модного CSS-инструмента.
